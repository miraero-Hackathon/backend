# API 성능 테스트 가이드

이 문서는 성능 테스트가 익숙하지 않은 팀원이 기본 용어와 진행 흐름을 빠르게 이해하기 위한 문서입니다.

이 문서는 성능 테스트의 개념과 지표 해석에 집중합니다. 실제 실행 명령, 파일명, 결과 저장과 팀 운영 규칙은 [k6 README](../README.md)를 참고합니다. 실제 부하 단계와 통과 기준은 `config`의 설정을 기준으로 합니다.

## 1. 성능 테스트를 하는 이유

기능 테스트가 API의 올바른 동작을 확인한다면, 성능 테스트는 사용자가 늘어도 API가 빠르고 안정적으로 동작하는지 확인합니다.

```text
부하 발생
→ 응답시간·처리량·실패율 측정
→ EC2·RDS 지표 확인
→ 병목 후보 분석
→ 개선 가설 수립
→ 개선 후 동일 조건으로 재측정
```

성능 개선은 단순히 코드를 변경하는 작업이 아니라, 측정 결과로 개선 효과를 검증하는 과정입니다.

## 2. 사용하는 도구

### k6

가상 사용자의 HTTP 요청을 발생시키고 다음 지표를 측정합니다.

- 동시 사용자 수
- 실제 초당 요청 수
- 응답시간
- 실패율

### AWS CloudWatch

k6로 부하를 발생시키는 동안 애플리케이션 서버와 데이터베이스 상태를 확인합니다.

- EC2 CPU 및 메모리
- RDS CPU 및 메모리
- DB 연결 수
- 읽기·쓰기 지연시간

EC2 메모리는 CloudWatch Agent 등 별도 수집 설정이 필요할 수 있습니다. CloudWatch만으로 원인을 확정하지 않고 병목 후보를 찾는 근거로 사용합니다.

## 3. 기본 용어

| 용어 | 의미 |
| --- | --- |
| VU | 동시에 동작하는 가상 사용자 수 |
| RPS | k6가 관측한 초당 완료 요청 수 |
| 평균 | 전체 요청 응답시간의 평균값 |
| p95 | 전체 요청의 95%가 완료된 응답시간 |
| p99 | 전체 요청의 99%가 완료된 응답시간 |
| 실패율 | 전체 요청 중 실패한 요청의 비율 |
| Threshold | 팀에서 정한 성능 통과 기준 |
| Think Time | 사용자의 다음 행동까지의 대기시간 (`sleep`) |
| Baseline | 개선 전후 비교에 사용하는 기준 결과 |
| 병목 | 시스템의 처리 성능을 제한하는 구간 |

`30 VU`가 `30 RPS`를 의미하지는 않습니다. API 응답시간과 Think Time에 따라 실제 RPS가 달라지므로 둘을 함께 기록합니다.

## 4. 테스트 종류

### Smoke Test

낮은 부하에서 인증, API 호출, 응답 구조와 k6 스크립트가 정상인지 확인합니다. 서버 한계를 판단하는 테스트가 아닙니다.

### Load Test

정상적인 서비스 사용 상황으로 정의한 workload에서 응답시간, 처리량과 실패율을 확인합니다. 성능 개선 전후의 주된 비교 기준인 Load Baseline을 여기서 측정합니다.

현재는 실제 운영 데이터가 없으므로 예상 사용자 규모와 API 호출 빈도를 가정해 팀의 기준 workload를 정합니다. 이는 실제 운영 트래픽이나 시스템의 최대 안정 처리량을 의미하지 않고, 개선 전후를 같은 조건으로 비교하기 위한 기준 부하입니다.

### Stress Test

부하를 계속 높이며 응답시간이 급증하거나 실패가 시작되는 지점을 확인합니다. 한계 분석이 필요한 핵심 API에 선택적으로 수행합니다.

구체적인 VU와 실행 시간은 예시 문서가 아니라 `config/profiles.js`를 기준으로 합니다.

```text
Load Test   → 정의한 기준 workload에서 안정성 확인
Stress Test → 부하를 높이며 시스템 한계 구간 탐색
```

Stress에서 100 RPS까지 안정적이었다고 해서 Load workload를 100 RPS로 정하는 것은 아닙니다. Load workload는 예상 사용 패턴을 기준으로 정하고, Stress 결과는 처리 한계와 병목 구간을 이해하는 데 사용합니다.

### 공통 Profile과 API별 Profile

공통 Profile은 여러 API의 초기 반응을 같은 낮은 조건에서 살펴보기 위한 탐색 도구입니다. 모든 API가 영구적으로 같은 부하를 사용해야 한다는 의미는 아닙니다.

API마다 호출 빈도와 처리 비용이 다르므로 탐색 후 API별 기준 workload를 정할 수 있습니다. 이때 실패 직전의 최대 안정 구간을 Load로 선택하지 않고, 개선 전후를 반복 비교할 수 있는 합리적인 부하를 선택합니다. 그보다 높은 한계 구간은 Stress에서 다룹니다.

### 합리적인 기준 workload

운영 트래픽 데이터가 없는 현재 단계에서 합리적인 workload란 실제 사용량을 정확히 재현한 값이 아니라, 개선 전후를 공정하고 반복 가능하게 비교할 수 있는 조건을 의미합니다.

다음 조건을 함께 만족하는 구간을 기준으로 삼습니다.

| 확인 항목 | 판단 기준 |
| --- | --- |
| 기능 정상성 | 모든 check 성공, 인증·응답 데이터 정상 |
| 실패 안정성 | 실패율이 등급 Threshold 이내이고 Timeout·예상하지 않은 5xx가 없음 |
| 측정 가능성 | 부하 증가에 따른 응답시간 또는 인프라 지표 변화가 관찰됨 |
| 자원 여유 | EC2·RDS·Connection Pool이 테스트 내내 포화 상태가 아님 |
| 표본 수 | 대상 API 요청이 p95·p99를 비교할 수 있을 만큼 충분함 |
| 반복 가능성 | 동일 조건 반복 시 주요 지표가 지나치게 흔들리지 않음 |
| 환경 일관성 | 데이터, 서버 사양, 실행 위치, CPU Credit과 외부 트래픽 조건이 유사함 |

초기 판단선으로 EC2나 RDS CPU가 장시간 `80%` 이상 유지되는지 살펴볼 수 있지만, 이는 절대적인 통과 기준이 아닙니다. CPU뿐 아니라 실패율, 응답시간, DB 연결 수, 지연시간과 회복 상태를 함께 판단합니다.

같은 조건의 세 실행에서 주요 지표가 중앙값 기준 대략 `±10~15%` 범위라면 비교하기 수월합니다. 편차가 크면 다른 부하 실행, CPU Credit, 이전 테스트의 영향, GC, 데이터 변화와 외부 요청을 먼저 확인합니다.

프리티어 EC2와 RDS처럼 버스트 가능한 인스턴스에서는 `CPUCreditBalance`가 부족한 실행과 충분한 실행을 직접 비교하지 않습니다. 인프라 한계가 먼저 나타났다면 애플리케이션의 최대 처리 한계로 단정하지 않습니다.

## 5. 어떤 API를 테스트할까

모든 API를 테스트하지 않습니다. 다음 조건에 해당하는 API를 우선 선정합니다.

- 호출 빈도가 높은 API
- JOIN이나 집계가 많은 API
- 대량 데이터를 처리하는 API
- 복잡한 트랜잭션이나 락을 사용하는 API
- 외부 API를 호출하는 API
- 서비스의 핵심 기능

단순 PK 단건 조회처럼 병목 가능성이 낮은 API는 우선순위가 낮을 수 있습니다.

## 6. 지표를 해석하는 방법

한 지표만 보고 원인을 확정하지 않습니다.

| 관찰 결과 | 병목 후보 | 추가 확인 |
| --- | --- | --- |
| p95와 RDS CPU·Read Latency가 함께 증가 | DB 조회 | 실행계획, 인덱스, JOIN, 조회 행 수 |
| p95와 EC2 CPU가 함께 증가하고 RDS는 여유 | 애플리케이션 | 연산, 스레드, 중복 처리 |
| DB 연결 수와 p95가 급증하고 Timeout 발생 | 연결 관리 | HikariCP, 트랜잭션, 연결 반환 |

CloudWatch 지표는 원인에 대한 단서입니다. 실제 원인은 SQL 실행계획, 애플리케이션 로그와 코드를 추가로 확인해 판단합니다.

## 7. 개념 적용 흐름

```text
대상 API 선정
→ Smoke Test
→ 공통 Profile로 낮은 범위 탐색
→ API별 비교용 기준 workload 확정
→ Load Baseline 3회 측정
→ 주요 지표의 중앙값 기록
→ 병목 후보와 원인 분석
→ 하나의 개선 가설 수립
→ 개선 적용
→ 동일 조건으로 3회 재측정
→ Baseline과 비교
→ 결과 기록 및 리뷰
```

이 흐름은 개념을 적용하는 순서를 보여줍니다. 팀에서 사용하는 구체적인 실행 순서와 결과 파일 규칙은 README를 따릅니다.

## 8. 실험 원칙

- 한 번의 실험에서는 가능한 한 하나의 개선 가설을 검증합니다.
- 개선 전후에 시나리오, VU, 실행 시간, 서버 사양과 데이터 조건을 동일하게 유지합니다.
- 중요한 실험은 3회 이상 실행하고 p95, 실제 RPS, 실패율 등의 중앙값을 대표값으로 사용합니다.
- p95뿐 아니라 p99, 실패율, 처리량과 인프라 지표를 함께 확인합니다.
- 로그인 요청이 `setup()`에 포함되면 대상 API 태그 기준 지표를 사용합니다.
- Stress Test는 부하가 허용된 환경에서만 실행합니다.

## 9. 핵심 흐름

```text
측정 → 분석 → 가설 → 개선 → 재측정
```

동일한 조건으로 재측정하지 않았다면 실제로 성능이 개선되었다고 판단하기 어렵습니다.
